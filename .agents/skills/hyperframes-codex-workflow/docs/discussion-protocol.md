# Animation Plan Discussion Protocol

## 类 PRD，但更轻

Animation Plan 与 PRD 的相似之处是：它需要先形成草案，再通过用户反馈逐步收敛需求。

不同之处是：它只讨论视觉叙事，不引入需求编号、完整验收矩阵、多级评审或审计流程。

## 第一版草案

Codex应先基于现有素材做出合理设计，不先提出一长串问题。

草案应：

- 覆盖完整叙事；
- 给出 Scene 顺序；
- 明确每个 Scene 的视觉目标和 Hero State；
- 标出可能使用的图片；
- 对未知项采用可修改的默认值；
- 将真正影响方案的歧义压缩为最多 3 个待决策项。

## 每轮讨论

用户反馈可能针对一行、一个场景或整体方向。Codex应：

1. 更新同一个 `ANIMATION_PLAN.md`；
2. 保留未被修改的已确认部分；
3. 回复中先列一行变更摘要；
4. 只展示变更后的相关 Scene 或 Asset Brief；
5. 仍有实质歧义时再列待决策项。

不要每轮重新输出完整 Profile、工作流或全部 Scene，除非用户明确要求查看完整计划。

## 有价值的讨论主题

- 信息是否被正确拆成 Scene；
- 某个 Scene 应让观众理解什么；
- Hero State 是否准确；
- 是否过度动画；
- 口播模板中的人物是否仍是主视觉；
- 纯 HyperFrames 是否有持续视觉锚点；
- 图片是否真正降低理解成本；
- 旁白和画面谁先承担信息；
- 转场是否与章节变化一致。

## 无价值的流程问题

不要让用户确认：

- CSS 属性；
- GSAP 精确参数；
- 文件命名细节；
- lint 命令；
- 每项测试是否执行；
- 是否“符合流程”；
- 不改变语义的微小布局调整。

## 批准识别

用户自然语言表达以下含义即可：

- 计划确认；
- 按此执行；
- 可以制作；
- 方案通过。

Codex将 `status` 更新为 `approved`，随后直接执行，不再要求第二次形式化确认。
