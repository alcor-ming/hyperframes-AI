# HyperFrames AI Work Router

This Skill is intentionally thin. The repository root owns the workflow.

## Runtime Boundary

Windows opens the actual production root and calls its root work.cmd directly. Tools live in runtime/ and .studio/; local configuration lives in .studio/.runtime/. Resolve the root from the launcher, not inherited session/HOME variables. Do not create or require a Harness session. Each command resolves inputs once; long-running Studio/render processes retain those inputs. Stop related processes before updating managed tools; do not hot-swap code or dependencies. Windows develops visual content in Work-local or registered AssetSource; WSL owns only Harness tools, contracts, host wiring and dependency assembly.

Preserve current M2–M3 code, frames, Scene/Anchor IDs, audio and accepted snapshots. Reuse a current Scene for the dynamic reference, not a fresh unrelated demo. Only actual tool/host/dependency defects go to WSL as frozen minimal reproductions; shaders, GSAP, Three.js and semantic-object design remain Windows content. Installed tools, accepted packages and vendor stay immutable.

A candidate is an independent direct-entry root with its own configuration, WorkStore, AssetStore and necessary source copies. Inherited asset defaults must not redirect Review into production. Review acceptance remains test-only and grants no production Finalize, archive completion or platform-draft permission. Old session data is read-only history, not an entry requirement.

## Start

1. Run `./work current`; when no Work is current, run `./work list` and do not guess.
2. Confirm `WORK.md` declares `"workflow":"hyperframes_video"`; route `podcast_quote_image` to its own Skill.
3. Follow root `AGENTS.md` and `.studio/workflow.md`.
4. Load the current `WORK.md`, `variant.yaml`, `SCRIPT.md`, one Recipe, and only the selected Profile resolved through `.studio/capabilities.yaml`. Treat the marked Scene index in SCRIPT as non-spoken planning input; use `work script text` for narration consumers.
5. Script defines this episode and each part's spoken content, whether written by the user or transcribed. If SCRIPT is empty but source text exists, organize it through the selected Script route before Research; do not require a user-authored visual brief or a fact-checking round. Create or load only Research material relevant to the current part/Anchor's visual needs. Load `ANIMATION_PLAN.md` for visual planning, affected-scope revision, or recovery, and `.studio/spec/hyperframes.md` for implementation and QA.
6. Load `hyperframes-anti-ppt` only when forming or reviewing the Animation Plan, or reviewing a Draft in Studio. Select animation-led or text-led as the film's main type independently from Template and Profile; recommend a type when unspecified and confirm it with the existing direction approval.

## Route

- For downloaded video, route `SCRIPT.md` through either multi-round `dbs` editing or timestamp-preserving `verbatim`; Script approval appears only when spoken text changed.
- Once the Script is settled, run `./work --work <work-id> --variant <variant-id> name "<core-topic>"` before Research. The CLI preserves the per-workflow three-digit sequence allocated by `work new` and leaves the Work ID unchanged.
- Research prepares sourced visual content and media for Plan: what concrete text, example, image, screenshot, video or data would make this part understandable? Complete narration can still need material; reuse sufficient existing material without mandatory browsing or images. In `RESEARCH.md`, organize presentation needs, findings, media evidence and actual open questions by Script part/Anchor. Wording and media are candidates, not mandatory screen copy. Plan selects content and presentation; return only for specific material needs found during design. Follow `.studio/workflow.md` for readiness and source ownership. Fact checks support selected material, with conflicts handled locally rather than becoming a script audit or blocking unrelated research.
- Before Plan approval, use `hyperframes-anti-ppt` to verify that the intended conclusion is expressed through the chosen text, media, operation, or motion, and that text which must be read has a real reading window. Merge concrete findings into `ANIMATION_PLAN.md`; do not require verbatim card-by-card repetition, a uniform transformation formula, or another approval artifact.
- The video workflow owns discovery, versioning and installation through the existing `component` CLI. Discover accepted assets from configured external sources and their metadata; bundled `.studio/components` is read-only legacy compatibility, not a fixed whitelist. Read matching `asset.json` and declared usage/example files for modules/media; legacy Components use `COMPONENT.md`, relevant Cases and necessary boundary Fixtures. A Case never widens the contract. `migration-ready` is not production acceptance: validate the required exact asset once at library level, not through repeated Work samples or a whole-library completion gate. Compatible asset additions do not require a Harness release. Keep Work dependencies in existing vendor / Binding / `COMPONENT_LOCK.json`; library updates do not replace fixed copies, and offline closed copies remain usable.
- Prefer semantic visual objects that explain one meaning and keep coupled internal behavior cohesive. Existing helpers and complete Scenes remain usable; extract helpers only for independent variation or real reuse. Work-local Scenes own this film's narration, layout and handoffs. Icons/images may be subjects, evidence or textures. Do not force five phases, both ratios, transparent roots or a whole-library migration. Use only deployed module/media contracts; do not claim Template/Recipe or Blender support.
- Keep the Scene brief, actual selected screen text, narration/visual selection and matching rationale in `ANIMATION_PLAN.md`: cite Script Anchors, selected Research entries and native media. Do not copy the full Script/Research or create a second text database. Do not transcribe every spoken sentence or restore removed attribution labels. Record exact assets, fit and limits or `custom:<slug>`. Decorative SVG/icons/images are allowed; do not require every visual to add a claim.
- When creating the Animation Plan, use DBS to write the final title, cover text, one-line summary, and content overview to `PACKAGE.md`. Keep the overview concise and split it by the main subjects or topics; introduce each Skill, tool, feature, or case separately when there are several. Do not retain the candidate list there.
- Keep talking_head or pure_hyperframes and one Profile, separate from the main type. Follow `.studio/workflow.md` for animation-led/text-led A/B duties and experimental ranges, not mandatory cut timers. Same-frame decoration does not count as B-roll; count only the main viewing task. Preserve original narration and total duration. Do not require a mechanism for every animation-led Scene; text-led cards generally have decoration and may briefly be text-only. Screen copy may omit setup, emotion, transitions and repetition without misleading or losing conditions that change the conclusion.
- Keep the whole frame from remaining completely static for more than 2 seconds while body text and individual objects remain stable for reading. Distribute content, keyword emphasis and restrained auxiliary motion over the full interval, rather than revealing everything early. Verify perceptible changes and reading comfort during actual playback, not tween counts; automatic tolerance is not established. No flashing, infinite decorative loops, drifting body text, filler copy or audio cuts to satisfy this rule. Do not add music/SFX by default.
- With Script and Research ready, select useful information per Scene, then match accepted assets or combinations against the intended relationship, actual text, optional explanations, media shape, ratio, available time and state changes. Record exact references and content bindings in the whole-film Plan. Existing fit is reused directly; parameter changes or ordinary overflow QA do not create another design approval. Asset acceptance or wiring alone is not a design gap.
- After the whole-film Plan, make exactly one real Scene dynamic reference, reusing current M2–M3 work where possible. Show actual text, canvas, motion and media positions. Use the existing audio crop when available; otherwise mark timing provisional. Keep stable semantic placeholder IDs, not fake resource paths. Do not render a multi-Scene montage as a disguised second reference.
- Describe principal motion through objects, relationships, start/end states and reading arrangements; give costly or novel effects a fallback when needed. Default to implementing uncertain effects first inside Draft. Use an early local experiment only for a risk that changes the overall decision, not as a new mandatory approval.
- Ask once for direction approval covering the Plan revision, main type, exact Scene preview and generated assets whose purpose, quantity, style and Asset Brief are specified. Do not ask for each such asset again; ask for unspecified purposes or materially exceeded quantities. Generated media must not impersonate real product screens, results or evidence; private data sent to a new provider still needs authorization. Do not add per-Scene approvals. Scene direction is never full-Draft authority; old kind=reference retains its non-playable meaning.
- Delegate only current effective type, Plan, corresponding Research selections, necessary Script/time evidence and assets. Do not give workers only the transcript and cues or copy all Research into each batch. Remove superseded requirements from editable briefs/contracts while preserving frozen history. Worker completion never replaces the main model's content acceptance responsibility.
- Use `preview open [current|plan-vNNN|draft-vNNN]` for the pinned official Studio; omitted target means current editable project. Registered versions open independent review copies, never hardlinks/symlinks into accepted snapshots or frozen assets. Return the actual Studio project URL, not a source HTML path or guessed port. Historical custom review requires `--legacy`; do not silently fall back. Use `preview context [target] --fields selection,lint --detail compact` for narrowly scoped lookup tied to the actual project/port; use full only when needed, and `preview stop [target]` for that preview process. Do not upgrade/download CLI dependencies during ordinary creation.
- Studio uses the returned isolated `browser_profile` with Chrome Do Not Track enabled. Automation using `--no-open` must reuse that profile and verify DNT before navigation; CLI environment opt-outs alone do not disable frontend telemetry.
- After direction approval, immediately expand all planned Scenes into a full planned-placeholder Draft. It must contain the whole narrative and actual implemented motion; permit declared media placeholders, temporary audio and agreed proxies, not hidden code errors or empty Scenes. This Draft adds no mandatory acceptance gate. Fill stable media IDs when ready, then submit a media-complete final Draft to the existing full-version acceptance and Final flow.
- After approval, reuse the shared theme and only explicitly matched local layouts. Assemble each Scene from its Plan, asset references and Binding, starting with the riskiest shot. Participants/connections, conditions/branches and feedback/results must remain visible relationships or states, not flattened generic text rows. An unsupported expression is a named Scene implementation gap, never a silent card fallback. Same-structure reuse is valid; cosmetic variation is not semantic implementation. The same model may adjust line breaks, grouping, labels and equivalent wording in place, updating the Research entry and its presentation. Plan may omit Research candidates freely; new claims need focused research. Only selection changes to confirmed conclusions or narrative need local user confirmation; approved visual-direction changes retain their existing review rules.
- Studio copy edits must update the corresponding Script/Research source or pause regeneration of that field. Do not let regeneration overwrite user corrections or create a second copy system in HTML. Rebuild affected MP4, screenshots and QA when source changes; old evidence cannot represent current code.
- Necessary structure changes are allowed without changing the approved visual result. Do not require missing production code to be backfilled into Plan. Use `preview diff <id>` for scoped changes. After an equivalent Research/project change, use `--compatible` only when narration, Anchors, and the accepted Plan's visual body are unchanged; only its `status`, `visual_plan`, `revision`, `script_revision`, and `research_revision` frontmatter fields may differ. Record the affected Scene and rationale. The runtime verifies frozen/current inputs, revisions, and project hashes and does not infer semantic equivalence. Compatibility carries the Accepted Plan into a new Draft; it never extends an Accepted Draft across source content or revision changes. Legacy records without frozen source inputs keep the original flow. Required media/effects must be complete for full-version acceptance and Final, not for rendering a declared full placeholder Draft.
- For formal audio, adjust reading holds, flexible motion and handoffs before assuming whole-scene time scaling. Preserve required text, complete audio and old Accepted Draft/Final snapshots.
- Resolve semantic cues deterministically from existing timestamps/section_map: Anchor plus character range or explicit occurrence, intended object event and offset. Map source trim/take/rate to engineering time once; subtract crop origin for a Scene preview without rewriting alignment. Removed words cannot supply cues. Quantize only at output fps. Key visuals and tracks must reconstruct from target time without seek callbacks. Music analysis is optional offline hash/parameter-cached work; missing music or Blender does not block nondependent production. Check real sound alignment, mapping and audible rendered footage, not matching labels alone.
- Keep time authorities separate: SCRIPT carries planning budgets, formal audio and `section_map.json` carry measured time, and the project timeline carries actual visual appearance and duration. Plan records only the needed basis and rhythm intent.
- Review the full placeholder Draft in Studio without a mandatory approval. Once media is complete, `preview register` without a file freezes an executable Studio Draft and its closed sources, with no whole-film Draft MP4/render receipt prerequisite. File-based registration remains compatible. Open that exact `draft-vNNN` with `preview open`, inspect the independent copy using `hyperframes-anti-ppt`, then `preview accept` that ID. Verify actual sound, continuous playback, seeking and dragging backward; local playback limitations may use a short audible export, never an undisclosed full-Draft export. Report unverified Windows/audio behavior honestly.
- Only a media-complete full Accepted Draft authorizes `preview render <draft-id> --output <final.mp4> --final`. Render the accepted snapshot, not changed editable code; keep the formal render receipt. Then inspect encoded streams, format, duration, full decode, representative frames and necessary audio before Finalize and automatic archive. Completing Final includes this local lifecycle unless explicitly limited, not publishing/uploading.
- Scope QA to impact: unchanged accepted work needs source/evidence applicability, local edits need affected states/Scenes and handoffs, shared layout/timeline/host changes need dependency-based regression. New encoding does not reopen accepted design; Finalize/archive verifies sources, render records, files, destination and lifecycle without another review/render. Fix real failures and re-render when needed.

Do not load Prompt libraries, subtitle generation, publishing, Examples, Migration files, all Profiles or all Draft/QA history during normal production. Image generation is only for assets authorized in the approved Plan; `design-taste-frontend` additionally needs an explicit approved Asset Brief request.
