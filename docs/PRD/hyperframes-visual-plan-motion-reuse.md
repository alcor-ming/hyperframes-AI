# HyperFrames AI：可执行视觉 Plan、信息型动效与效果复用升级 PRD

- 文档版本：v1.0
- 日期：2026-09-05
- 用途：交给 Codex 在现有仓库上迭代的需求与验收依据，不是另起项目的架构蓝图。
- 目标仓库：`alcor-ming/hyperframes-AI`
- 公开仓库审查基线：`fc65f01dbd74b25b6b19ae1019efe1f04a7bb526`。Codex 实施时以本地真实版本为准，先核对差异，不回退本地新能力。
- 主场景：AI 科普、Skill 介绍、工具机制讲解与工作流说明。
- 主要影响：`hyperframes_video`。不改造 `podcast_quote_image` 的内容、排版或审批流程。
- 范围声明：组件库只给选型、复用与沉淀方向；不替用户预设组件目录，不批量重建现有组件。

## 0. 产品决策摘要

本轮不以“更多规则、更多组件、更多动画”为目标。核心交付是：**让用户在整体制作投入扩大前，看见真实内容下的完整视觉与动作；让确认过的实现直接进入 Draft；让文字信息与动效共同解释内容；让常用效果可以再次调用。**

确定四项产品方向：

1. 将纯文字 Animation Plan 升级为“文字语义说明 + 同源可播放视觉预演”，替换原 Plan 的确认方式，不增加一层审批。
2. 采用“文字承载精确信息、动效解释关系、稳定窗口支持阅读”的信息型动效设计，反 PPT 不等于少文字，也不等于每场强制复杂变形。
3. 完整叙事组件与底层效果分别复用：前者由真实案例验证，后者可先复用 GSAP 动作、Three.js 场景效果和镜头行为。
4. 反馈定位到 Scene、对象或时间区间；已经确认且未受影响的场景保持不变，避免局部意见触发整片重做。

本 PRD 对既有规则的一项明确变更：**允许在 Plan 批准前，为可执行视觉预演创建 Work-local HTML、绑定候选资产和实现必要动效。** 未批准的是最终视觉方案，不是所有代码。禁止在未批准时进行与验证无关的整片高成本精修、覆盖历史快照或修改公共冻结资产。

## 1. 问题、依据与不确定性

### 1.1 已知情况

用户确认当前返工严重、组件复用较少，文字 Plan 不能展示实际效果，主要内容需要同时保留丰富文字与具有解释力的动画。

公开基线的 Animation Plan 模板主要记录 Scene、Anchor、Hero State 和组件入场；工作流要求批准 Plan 后才能正式制作 HTML。[R1][R2] 这意味着可感知效果主要在后续 Draft 中被检验。

现有 Anti-PPT Skill 强调时间中的视觉事件，但同时要求始终采用含“不可逆变化”的场景公式，并把部分排版结构直接列为禁用模式。[R3] 这些规则需要改成针对信息表达的判断，不能机械用于每一类知识内容。

现有主 PRD 已确定 Profile / Background / Component 分工、画幅独立实现和历史 Work 冻结。[R4] 本轮保留这些方向，不以轻量化名义删减未来设计。

### 1.2 待验证的根因假设

| 假设 | 本轮如何验证 | 不能据此得出的结论 |
|---|---|---|
| 真实动效看得太晚，导致后期方向性返工 | 把新动效、复杂文字和场景交接提前放进同源预演 | 不能保证预演后完全不返工 |
| 组件过于贴合某段原稿，换内容后无法适配 | 用不同长度、信息形态的真实输入试装候选组件 | 不能据此批量拆掉全部组件 |
| 组件检索只看名称或效果，忽略承载能力 | 在当前真实文字、时长、画幅中预演匹配结果 | 不能靠强制复用率解决适配问题 |
| 隐喻、文字、镜头同时争夺注意力 | 检查真实速度下的阅读与焦点迁移 | 不能简单得出“必须删字”或“必须减少所有动画” |
| 修改范围不清，已确认片段被重新生成 | 对局部改稿记录受影响 Scene，并检查邻接交接 | 不能把局部反馈变成全局禁止规则 |

没有读取本机私有 Work，也未执行本机渲染。本轮的效果改善是需要验证的产品假设，不承诺固定比例的时间节省。

## 2. 目标、非目标与保留边界

### 2.1 目标

- 在 Plan 确认时，用户已能看到各 Scene 的实际文字布局、主要动画、Three.js 效果、节奏和交接，而不是靠文字想象。
- 从预演进入 Draft 时，沿用同一套场景实现、资源和参数，不“参考预演重新写一遍”。
- 增加 GSAP 的表达能力：除入场外，支持重点迁移、关系呈现、对象转化、证据放大与连续交接。
- 保留应出现的术语、论点、条件、操作步骤、例子与边界，不用空泛视觉替换实质信息。
- 常用 Three.js 效果可以以有限参数接入不同内容，可靠拖动、回放和渲染。
- 新增局部修改能力与少量结果记录，而不是新增复杂任务系统。

### 2.2 非目标

不新增第三条工作流；不开发通用视频编辑器、节点编辑器、在线 Registry、向量检索系统、自动审美评分器或多代理串行审查系统。不以本轮为由批量创建几十种组件或 Three.js 特效。不建设新渲染引擎，不强制迁移到 React、WebGPU 或其他技术栈。不把分段编码缓存作为局部改稿的前提。

### 2.3 保留的约束

保留 Work / Variant、外部私有 WorkStore、稳定 Scene ID 与 Script Anchor、Draft 快照、Final 历史和可恢复归档。口播改写仍遵守已有授权；不生成或烧录传统底部字幕。画面内的解释性文字不是底部字幕，不受此排除项限制。

保留 `talking_head` 与 `pure_hyperframes` 两模板。保留组件的画幅独立设计，不为追求通用率把多个画幅退化成自动缩放。保留原公共资产迁移范围与验收约定：本轮可以分段验证新能力，但不得把试验性接线冒充整库迁移已完成。

公共库只保存可公开的实现、合同、必要来源信息及脱敏样例。真实作品的文案、截图、素材、预演、反馈和成片仍在 WorkStore。安装第三方效果前核对许可和依赖来源；“公开可访问”不等于“可以任意打包”。

## 3. 工作流：从文字审批改为真实效果确认

### 3.1 新工作流

```text
内容输入 / 已有文案
  → 意图与必须呈现的信息明确
  → Script / Research / 实际媒体按现有规则就绪
  → Animation Plan + Work-local 场景实现并行形成
  → 同源 Visual Plan：完整场景预演 + 实际文字 + 动效 + 场景交接
  → 用户一次确认 Plan（围绕可见效果，不逐项盖章）
  → 同源精修、媒体完善、完整 Draft
  → 用户接受 Draft
  → 正式配音接入或同步修正、Final QA、正式渲染、归档
```

已有正式音频时提前用于预演。`talking_head` 继续以实际人物媒体和对齐结果设计解释层；`pure_hyperframes` 保留先视觉、后正式配音的路径。

预演是原 Plan 的可视化表达，不是 Plan 后面新增的 Motion Plan 审批。Draft 确认检查整片完成度和实际差异，不重复询问已确认的创作方向。

### 3.2 预演必须解决什么

**所有 Scene 都能被查看，所有决定视觉方向的实际效果都能被播放。** 不允许只做好开头，后面继续写“待实现高级动效”却要求批准整片。

采用按风险分配制作深度，而不是按风险决定是否展示：

| 内容 | Plan 阶段要求 | 可留到 Draft 的内容 |
|---|---|---|
| 已验证组件的新用法 | 绑定当前实际文字、素材位、画幅与时间，实际播放 | 不改变表达的细节修整 |
| 新 GSAP 机制、新 Three.js 效果 | 实现能看见核心行为、风格与时序的真实样段 | 非关键光影、细微 easing、性能精修 |
| 高信息密度段落 | 完整必须上屏文字、真实字体排版、稳定阅读时段 | 不改变层级和含义的换行调整 |
| 相邻 Scene 交接 | 连续播放交接；验证对象和信息是否延续 | 不改变转场类型的节奏微调 |
| 真实截图、视频证据 | 决定版式或论证的素材应使用真实输入 | 与语义、构图无关的编码质量提升 |
| 缺失的关键素材 | 标明缺失与影响，不把占位当作效果获批 | 仅在明确保留该不确定性时后补 |

无风险的既有设计不额外生成多个方向；确实影响整体风格的新机制，可少量并列比较。默认给一个推荐方案，不给每个 Scene 都做三套完整设计。

### 3.3 Visual Plan 的界面要求

优先复用当前 HyperFrames 的预览、播放器、定位和截图能力；只有当前版本缺少必要功能时才加薄查看层。

最小能力为：完整顺序播放、暂停、时间轴拖动、Scene 定位、该 Scene 的关键阅读帧查看，以及实际展示尺寸下的可读性检查。复杂效果应同时能看过程与停留状态，静态 contact sheet 只能辅助，不能替代动效预演。

画面旁只展示当前 Scene 的视觉目标、必须呈现的信息、尚未验证的差异。后续修改默认聚焦变更片段，不强制重看未变化部分。不建设带手工拖拽排版、节点图和全功能编辑能力的新产品。

多 Scene 预览不得让所有 Three.js 缩略图同时常驻运行。可以使用静态缩略图，进入 Scene 后再启用实际播放；具体资源复用方式由实现选择。

### 3.4 低成本预演不等于低保真设计

预演可以减少编码开销、延后非关键精修，但应保持正式画布尺寸下的布局、字体、换行、内容、镜头和时间逻辑。查看窗口可以缩放，不能因 CSS 视口变化使预演与成片采用不同排版。

凡直接决定视觉判断的透明度、遮挡、材质、景深、粒子密度、镜头行为，不能用明显不同的替代效果获得批准。较低编码质量可能降低可读性时，提供正式画布尺寸的关键帧辅助检查。

预演需要真实制作投入，这是把不确定性前移，不是免费消除它。成效必须以“从开始到最终接受的总投入”衡量，不能只把返工从 Draft 挪到 Plan 后就宣称成功。

### 3.5 同源复用与审批记录

`ANIMATION_PLAN.md` 继续是视觉意图、Scene 选择和用户决策的语义真源；Work 的场景源码与 Binding 是可执行真源。预览页只投影现有数据，不成为第三份可独立编辑的方案。

Plan 确认应关联对应的预演版本及源快照。复用现有快照和元数据能力记录这一关系，不另造签名、证明链或层层 receipt。Plan 预演与正式 Draft 必须在类型或字段上区分，不能把一次 Plan 接受误写成 `accepted_preview`，进而放行 Final。

预演获批后，Draft 继续修改同源 Work 工程。允许更新必要的内容绑定、非结构性布局、同步与质量参数；不允许为了“正式化”重新生成已经确认的场景。

## 4. Animation Plan 的最小内容调整

不新增独立的 `MOTION_PLAN.md`、`SCENE_SEMANTICS.md` 或手工维护的第二份 Scene 数据库。增加的信息仍归入现有 Plan，并按需生成查看数据。

| 项目 | 内容要求 |
|---|---|
| 作品目标 | 受众、看完应理解什么、必须保留的信息、不能采用的表达 |
| Scene 与 Anchor | 稳定 ID、口播引用、对应研究依据；不复制整篇口播 |
| 上屏信息 | 必须可见的术语、结论、步骤、条件、例子；给出当前实际画面文字或其唯一绑定引用 |
| 表达职责 | 本段由文字解释什么，由操作/动效演示什么，是否为示意 |
| 动态与阅读状态 | 主要状态变化、信息焦点、可读稳定区间、必要交接 |
| 资产与复用 | 组件、效果或 Work-local custom 的真实引用；不写虚假的“已复用” |
| 预演定位 | 对应预演版本、Scene 或时间位置，以及未解决差异 |

上屏文字需要进入具体排版，不以“后续补充说明”代替。实现应选定唯一维护位置，Plan 引用该位置或由其生成展示，避免一段文字在 Plan、JSON 和 HTML 中被手工维护三次。

Scene 仍是唯一强制层级。只有复杂场景需要时才细分 Beat；不要求每一场都填固定数量的状态、动词、拒绝候选或证明条目。

## 5. 文字丰富与反 PPT：信息型动效规范

### 5.1 三条设计原则

**信息先完整，注意力再编排，动画服务于解释。** 三者不是先写一屏文字、再额外加粒子的顺序，而是共同设计时间中的表达。

“丰富文字”指一条视频实际传递了足够具体的信息，不意味着所有段落必须同时出现在一帧。“反 PPT”指画面不只是固定页面中逐项进入的信息块，不意味着禁止文字、列表、对比表、截图、卡片或稳定阅读状态。

视觉目标不是把动画退回朴素淡入。允许有质感的动态构图、空间层次、节奏对比和跨对象交接；丰富动效与稳定阅读应在时间、区域和焦点上协调，而不是互相取消。

不能用删掉限制条件、隐藏必要步骤、把完整解释改成几个口号来换取画面清爽。用户要求必须上屏的信息，不得未经确认改成“只在口播中说”。其余内容允许合理归纳，但必须保留原意与重要限定。

### 5.2 文字、动效与证据的职责

| 表达渠道 | 主要职责 | 不应承担的职责 |
|---|---|---|
| 标题、段落、步骤、标注 | 精确描述术语、动作、结论、条件与限制 | 每一行都持续运动来制造动感 |
| GSAP / SVG / DOM 动效 | 引导焦点，揭示关系，保持对象连续性，演示状态变化 | 用无意义入场替代解释 |
| Three.js | 在确有价值时表达空间层级、聚合分布、路径、遮挡或镜头变化 | 接管所有正文、以旋转粒子代表所有 AI 机制 |
| 截图、录屏、实际输出 | 为操作、结果和差异提供可核验依据 | 以程序模拟界面冒充真实产品能力 |

这些是职责区分，不要求每个 Scene 固定采用三层画面或同一种左右分栏。

### 5.3 先分配信息，再设计运动

在现有 Scene 中区分三类内容：主命题、支撑解释、条件或证据。不是所有场景都需要三类齐全；有需要就具体呈现，不能为了模板凑齐。

优先采取以下方法保留信息密度：

- 按含义分组显现，而不是逐字、逐标点播放整段正文。
- 当前解释清晰可读，已解释内容可以留作稳定上下文；下一组出现时明确转移焦点。
- 通过替换、重组、局部放大或展开显示细节，而不是不断往同一页面堆卡片。
- 术语、对象和对应图形保持一致的标注与关联；文字不因隐喻变化丢失指向。
- 实际操作展示可以短暂停留并给出完整说明；“暂停以便理解”不构成反 PPT 失败。

信息太多时，先调整分组、场景内部时序与版面，再判断时长是否足够。不能默认无限缩小字体，也不能为了保持动画速度省掉必要内容。确实无法在既定音频中容纳时，只针对该段提出取舍。

### 5.4 阅读窗口与注意力平衡

每一组必须上屏的信息，都应有可辨识的稳定阅读区间。该区间内正文不应持续漂移、缩放、乱码变换或被景深模糊；镜头与特效不能不断把视线拉离正文。

文字进入新的复杂解释时，降低其他区域的运动强度；需要观察操作或空间变化时，相关说明可以保持稳定，用小范围强调同步解释。轻微环境运动可以继续，不要求整个画面静止。

不设置所有 Scene 通用的字数、字体大小、文字占比、动画占比或固定停留时长。评估依据是当前画幅、真实字数、受众、媒体节奏、排版和实际显示尺寸。代码可报告遮挡、越界、短暂显示等问题，不能把经验阈值伪装成自动审美结论。

原模板中的“全部主动作在结尾前 0.4 秒结束”不再作为全局阅读规则。结尾短暂停顿不能替代贯穿场景的阅读设计；可保留为特定组件的既有动作合同，使用时仍检查是否足够承载当前内容。[R1]

### 5.5 动效隐喻必须有信息映射

每个关键隐喻需要说明：画面中的对象代表什么、动作对应何种关系、观众应得出什么结论。用一句话或简短 Scene 注记即可，不强制新增结构化文件。

例如，“资料被筛选”可以表现为候选项保留或排除，文字同时解释筛选依据；不能只让粒子进入一个发光球，就声称已经解释了检索、推理或事实核查。

对并列功能保留并列关系，对比较保留比较关系；只有确有依据时才表现为因果或必经顺序。不把工具串联的视觉隐喻误写成其真实产品能力。概念示意、模拟操作、真实录屏应可区分。

数字、百分比、速度、成功状态和排名必须有实际依据，或者清楚标记为演示值。取消对所有机制套用 `0 → 100%` 进度条的倾向；无法定义进度时，使用阶段、选中、传递或状态变化，不制造精确度。

### 5.6 正反示例

| 内容 | 可采用的表达 | 应避免的表达 |
|---|---|---|
| 一个 Skill 如何处理输入 | 输入对象沿真实步骤变化，文字逐步解释输入、动作、输出与限制 | 标题下面三张卡片依次弹出，内容与运动无关 |
| 几个 Skill 的适用场景 | 保留对比项，用焦点迁移和局部展开展示差别 | 为“连续感”把独立工具硬接成工作流 |
| 资料筛选或聚合 | 候选项有可追踪身份，筛选原因与结果同步标注 | 粒子随机聚散，观众看不出什么被保留 |
| 真实操作证据 | 放大实际相关区域，稳定显示注释，结束后收回上下文 | 整页截图快速缩放，文字既看不见也没时间读 |
| 机制的局限 | 正文清晰保留条件，相关对象在同一上下文中标出限制 | 只显示一个醒目的结论，把限制隐藏或口号化 |

### 5.7 一个 Scene 的示意样例

以下仅说明设计方式，不替用户预定组件。主题为“一个已核实的素材整理 Skill 如何工作”；实际能力、文案与结果必须以当前 Script / Research 为准。

| 示意区间 | 画面行为 | 可见文字与阅读安排 |
|---|---|---|
| 0–4 秒 | 显示输入材料，建立一个可追踪的材料对象 | 标题与完整输入条件稳定出现，如“输入：正文、来源地址与已有标签” |
| 4–10 秒 | 保留材料身份，突出正在处理的字段；GSAP 将相关信息局部展开 | 显示实际处理规则，而不是只有“智能整理”四个字；已讲清的标题留作上下文 |
| 10–16 秒 | 合适时由 Three.js 或 SVG 表现分组、归位，说明文字不随空间对象旋转 | 标注输出结构与来源保留方式；动作结束前后都能对应到原材料 |
| 16–22 秒 | 输出进入稳定阅读状态，并衔接下一个例子 | 显示必须保留的限制，例如人工核对要求或适用范围，不以特效替代 |

这里的时间只是示意，不成为模板常量。一个短 Scene 可以更简单，一个复杂 Scene 可以有更多信息阶段；没有必要时不使用 Three.js。

## 6. GSAP 能力升级方向

### 6.1 从“入场集合”升级为“可复用解释动作”

本轮优先支持下列能力类别，不要求一次性全部封装为公共 API：

| 能力 | 适合解决的问题 | 内容保护要求 |
|---|---|---|
| 焦点迁移、重点标注 | 让读者知道此刻正在解释哪一部分 | 其他必要文字仍可识别，不全部模糊消失 |
| 对象连续转移与路径运动 | 输入到输出、数据传递、材料归位 | 保留对象身份，不暗示不存在的因果 |
| 布局重组与比较展开 | 在相同空间承载更多解释或切换比较维度 | 重组后完整内容可读，不把整个正文持续做 FLIP |
| 证据放大、局部揭示 | 解释真实截图、代码或结果 | 关键证据不能在停留不足时快速闪过 |
| 关键词与图形关联 | 解释术语、条件与对象关系 | 关键词是完整解释的导航，不是正文替代品 |
| 有意义的跨 Scene 交接 | 把上一段结果带入下一段问题 | 不把所有内容强行串成同一套视觉故事 |

允许丰富的 easing、适当的预备动作、跟随和收束，但按内容需要选择，不设置“每场至少几个 tween”“每个组件都必须独立入场”的指标。

### 6.2 复用方式与技术边界

优先把已验证的动作封装为返回有限 timeline 的小函数，或在适合时使用 `gsap.registerEffect()`，而不是新建通用动画引擎。GSAP 官方支持注册可复用效果和基于状态的 Flip 过渡；是否引入插件应按本项目锁定版本、部署方式和实际场景决定。[T1][T2]

用于普通交互网页的动画示例不能原样当成视频效果。正式合成的状态必须能被直接定位，不依赖用户滚动、鼠标悬停、滚轮或实时事件。

遵守当前 HyperFrames 对 timeline 注册、同步构建和资源就绪的实际要求；异步资源通过既有就绪机制处理，不在抓帧过程中才临时拼装时间线。

同一个属性在同一时间由一个清晰的控制者拥有。组件内部动作与 Scene 编排通过明确的开始时间、局部时间或参数衔接，不叠加多个互相覆盖的 timeline。

涉及 Flip、动态排版或文字拆分时，在资源和布局就绪后确定必要状态，再构建可 seek 的动画；不能在某次播放回调里才修改 DOM，使随机跳转时缺失正文或状态。GSAP 的 `seek()` 默认抑制回调，因此不能把渲染关键更新仅放在 `onUpdate`、`onComplete` 等回调中并假定所有抓帧都会执行。[T3]

## 7. Three.js 常用效果复用

### 7.1 定位：效果部件，不是新的一套场景系统

Three.js 效果是可由 Component 或 Background 组合使用的实现模块。它不能反向拥有整条视频的叙事、正文、Profile 或全局时间轴。

由承载者决定效果职责：承担叙事、处理关系或主体空间变化时归属 Component；仅提供环境时归属 Background。不得以“效果层”为由绕过现有前景/背景边界，增加一个到处改动场景的全局管理器。

文字默认继续由 HTML / SVG 排版，Three.js 负责其擅长的空间表现。必要的短标签可以与三维对象绑定，但长段中文不默认转成旋转的 3D 字或纹理正文。

### 7.2 候选方向

以下是按真实案例选择的方向，不是本轮必须完成的效果清单：

| 效果方向 | 适合的解释目的 | 边界 |
|---|---|---|
| 可控粒子或点集汇聚、分散、筛选 | 表现集合、分组或候选选择 | 粒子需要被标注或与信息对象对应，不能只是装饰 |
| 节点、路径与信号传递 | 表现资料流向、分支或协作关系 | 不把示意网络当成真实神经网络内部机制 |
| 层叠展开、空间拆解 | 表现不同层次、组成关系与输入输出 | 必须保留层名和对应说明 |
| 对象变形与结果归位 | 表现结构转化与组织结果 | 形变本身不能替代转化规则说明 |
| 受控镜头、聚焦与浅景深 | 引导查看对象的局部和整体 | 正文不跟随镜头丢失，不靠景深掩盖必要信息 |

首轮从真实 Work 选最有价值的一到两个效果验证即可。没有真实素材时，可用脱敏替代用例验证技术链路，但应明确它不是已证实的真实生产复用。

### 7.3 最小效果合同

只定义接入职责，不要求立即建立复杂 schema 或插件平台：

- **初始化**：接收宿主、输出尺寸、主题参数、必要资源与固定 seed；状态不依赖另一份 Work。
- **时间求值**：接收可确定的 Scene 局部时间，直接得到这一帧的对象、镜头和 shader 状态。
- **有限配置**：只暴露真实需要变化的对象数量、路径、分组、密度、色彩映射、动作区间等，不为所有可能性添加参数。
- **生命周期**：有明确的载入就绪、显示/隐藏和释放行为；销毁时清理自身资源和监听器，不能释放其他组件共享的资源。
- **依赖与归档**：效果代码、必要 shader、模型、纹理及版本引用进入既有 Work 快照和依赖闭包，不依赖运行时去网络临时下载。

画幅适配由宿主的已设计实现负责；底层数学或绘制逻辑可以共享，但不因此取消 `4x3` 与 `16x9` 的独立构图。

### 7.4 与 HyperFrames 的接入

上游现有 Three.js 适配说明提供 `hf-seek` 和 `window.__hfThreeTime` 的逐帧驱动方式。[T4] Codex 应先检查本机安装版本和真实适配器，再决定接入位置；上游存在不等于本地安装已经支持。

优先复用既有适配器，统一 DOM / GSAP 与 Three.js 的帧时间。要验证全局时间到 Scene 局部时间的转换、偏移、暂停、重定时，以及同一帧中参数更新和 WebGL 绘制的顺序，不能只注册一个事件就宣称混合渲染完成。

禁止把 `Date.now()`、实时 delta、独立的 `requestAnimationFrame()` 或 `setAnimationLoop()` 当作成片动作的时间权威。可使用固定 seed 生成初始数据，再从时间计算状态；不能依赖“先播放上一帧”才能得到正确下一帧。

依赖历史帧的物理模拟、反馈 shader、拖尾或累积采样不进入首轮，除非能重建任意时刻的结果或提前烘焙。固定初始化、资源就绪和有限时长；不用无限 repeat 填充场景。

主库与 addons 的版本保持一致并固定在项目依赖中。渲染尺寸、像素比和必要色彩配置由工程控制，不随打开预览的屏幕设备随意变化。Three.js 提供显式绘制和资源释放 API，具体组合仍须在本项目实际环境验证。[T5]

### 7.5 不可用时的处理

Three.js 出错不能阻止不依赖它的普通 GSAP 工作。该效果不得悄悄变成静态图还登记为原效果通过。

若已批准方案包含明确且等价的降级表现，可以使用并记录实际输出；否则只报告受影响 Scene，并提出具体替代。主视觉或表达发生实质变化时需确认该部分，不重启整个作品审批。

## 8. 组件库通用率：本轮只确定方向

### 8.1 分开理解三种复用

| 类型 | 真正复用的内容 | 适用方式 |
|---|---|---|
| 完整叙事组件 | 信息结构、Slot 合同、布局、动作与交接 | 内容形态确实匹配时直接使用 |
| 动作与效果模块 | GSAP 动作、Three.js 绘制与时间行为 | 由不同组件或 Work-local 场景组合 |
| 案例与设计经验 | 如何表达某一信息关系 | 用于参考，不登记为代码复用 |

复制一份案例再重写内部代码，不等于调用了同一组件。一个效果被很多不相关场景强行使用，也不代表有效复用。

### 8.2 面向 AI 科普与 Skill 介绍的选型方向

优先从“需要解释什么关系”发现候选，例如输入—处理—输出、筛选、比较、分支协作、证据引用、信息回写和结果复用；不要只按“玻璃卡片”“发光粒子”或某个 Skill 名称分类。

匹配时同时看当前画幅、文字长度与信息形态、素材形态、可用时间、进出场关系和不适用条件。Profile 不应成为语义组件是否可用的唯一依据；主题兼容沿用现有主 PRD。[R4]

候选必须在当前文字与资源绑定后实际预览。默认给最合适的候选；只有明显存在取舍时再比较少量备选。不要求 Agent 为每场输出冗长拒绝清单。

### 8.3 保持可改，但不破坏冻结

优先通过 Slot、参数和组合适配。若一个长解释超出组件能力，应选择更合适的布局、组合或 Work-local custom，不为了塞进组件删掉关键信息。

需要改内部实现时，从原组件明确派生到 Work-local custom，记录来源，不原地改写冻结 vendor，也不强迫每次试验先发布一个新公共版本。新公共 Release 继续走已有设计与验收边界。

跨案例反复出现的稳定结构再抽取公共能力。可将“两次不同真实用途仍能不改内部实现”为优先沉淀信号，但不是所有开发都必须等待的硬门槛。测试样例中的两次绑定只证明可配置，不证明生产中已经复用成功。

### 8.4 本轮不交付什么

不固定组件总数、命名、分层数量或强制复用比例。不要求用户先完成整库设计才能使用新预演流程。不把已有未来组件清单删掉，不把用户在本地找出的案例偷偷替换成 Agent 自选的一套模板。

本轮最多补足影响真实使用的检索、绑定、可用状态与预览接线；具体组件设计仍由用户的本地真实案例驱动。

## 9. 局部修改与重定时

### 9.1 反馈的最小绑定

反馈至少能定位到当前预演/Draft 版本及 Scene；有需要时进一步定位时间区间或对象。可直接从播放器位置复制简短定位信息，不要求复杂批注系统。

例如：“S04，18.2–23.5 秒，保留这两段文字，改掉卡片轮流入场，资料筛选过程要看得见。”这授权的是该段视觉调整，不是重写全文或禁用整个项目的卡片。

### 9.2 修改传播规则

| 修改 | 处理范围 | 是否重新确认 |
|---|---|---|
| easing、换行、同语义强调、边距修复 | 当前 Scene，必要时检查交接 | 不新增审批，展示实际差异即可 |
| 调整某个效果的局部参数，不改变主视觉与含义 | 当前效果及对应 Scene | 不重复确认整片 |
| 改变隐喻、主构图、视觉目标或新换 Three.js 主效果 | 当前 Scene 与受影响交接 | 只确认变更部分，更新现有 Plan |
| 更换配音但语义结构不变 | 相关时间映射、阅读窗口与交接 | 不重新选择全部组件或视觉方向 |
| 改变口播事实、信息目标或整体结构 | 对应 Script / Research / Scene；确有全局影响才扩大 | 沿用既有内容确认边界 |
| 升级公共效果或组件 | 默认不传播到已冻结 Work | 用户明确要求采用时才更新并检验差异 |

局部改稿不等于已经实现视频分段缓存。即使最终仍整片重新编码，也应只修改必要源码、只重新讨论实际变化的设计。

### 9.3 正式配音接入

不默认把全场做统一 `timeScale` 拉伸。应区分表达动作、稳定阅读和交接：优先调整可变停留，再调整可变动作，检查剩余空间是否足以阅读。

如果当前组件只支持整体缩放，也应检查其动作速度与文字阅读是否仍合理。确实超出能力时，只处理该 Scene；不得静默截断配音、删掉必要上屏内容或把已经确认的设计全部作废。

精确到帧的时间映射由现有渲染与媒体对齐机制决定，不能把本 PRD 的示意秒数变成硬编码节奏。

### 10.1 Plan 预演的代码边界

现有正式 Draft 的批准检查继续有效。为预演增加用途区分：它可以在 Plan 未获批时创建，但仍要求当前 Script / Research 按既有路径就绪，并验证资源与引用有效。

如果候选组件安装入口当前只允许 Plan 批准后执行，应补足“预演用途的受限 Work-local 绑定”，而不是把正式生产的批准检查整体删除。公共 Release 验证、路径约束和冻结资产不变性仍有效；预演也不能把未正式可用的资产冒充库中已批准组件。

无必要时不增加 CLI 命令。需要增加时延伸现有 preview 子命令；命名由 Codex 与当前 parser 对齐。本文件没有宣称任何新增命令已经存在。

### 10.2 快照与渲染

Plan 的确认快照与 Accepted Draft 的快照使用同一套基础机制，但各自用途明确。扩展既有快照闭包纳入实际需要的效果模块、shader 和媒体资源，不设计第二套锁文件系统。

Final 继续从 Accepted Draft 派生，记录实际使用的源码与媒体版本、渲染参数和输出摘要；允许批准范围内的重定时，不原地覆盖 Accepted Snapshot。不能只由 Agent 写一句“源自已接受版本”，而缺乏实际生成关联。

依赖变化的检测针对当前使用内容。无关公共库更新不应使已冻结 Work 无法预览或交付。

### 10.3 规则与自动检查的职责

代码负责确定性检查、产物和路径完整、明确状态及安全边界；Agent 负责设计判断和具体问题修正；用户负责方向性选择与成片接受。

Anti-PPT 不再为了得到 `PASS` 循环重构。缺字、错误关系、遮挡和未实现的关键效果是需要修复的问题；“可能更好看”的建议不能自动使已确认方向失效。不增加独立审查 Agent、打分排行榜或新的用户证明步骤。

## 11. 验收场景

自动化测试与人工视觉验收分别报告，不能互相冒充。下列验收是结果要求，不是每条作品都要向用户展示的清单。

| ID | 验收场景 | 通过条件 |
|---|---|---|
| A01 | Plan 尚未批准 | 可生成真实 Work-local 视觉预演；不能因此直接 Finalize |
| A02 | 完整 Scene 覆盖 | 每个 Scene 都可定位、播放；主要动作、关键文字与所有交接均可见，未验证项明确标注 |
| A03 | 高信息密度 | 必须上屏的信息实际出现；无删掉关键条件、无限缩字或只在暂停状态才可读的问题 |
| A04 | 文字与动效平衡 | 复杂文字有稳定窗口；运动对象与解释能对应；稳定表格或证据页不因形式被强制返工 |
| A05 | 同源推进 | 从 Plan 进入 Draft 沿用被确认的代码和 Binding；精修差异可说明，不重写无关场景 |
| A06 | GSAP + Three.js 混合求值 | 同时验证正常播放、直接跳入中间、倒跳、再播放；文字和 WebGL 同帧同步 |
| A07 | 效果时间确定性 | 在相同固定渲染环境按 `[t3, 0, t1, t3]` 等顺序采样，同一时间状态一致；不依赖先播放前面帧 |
| A08 | 依赖与资源 | 当前 Work 资源闭合；无抓帧时网络下载；切换/销毁不会遗留持续运行的监听和无界资源增长 |
| A09 | 真实或候选复用 | 同一个效果实现用于不同文本或布局绑定，无内部重写；区分技术样例与真实 Work 复用 |
| A10 | 局部改稿 | 修改指定 Scene；未受影响的源码、内容和资产版本不变，受影响交接有检查 |
| A11 | 配音重定时 | 动作、阅读与交接仍合理，无截断音频、删关键信息或整片重新选型 |
| A12 | 旧 Work 与另一工作流 | 旧快照/Final 不改写；原有视频路径仍可工作；播客图文行为没有非必要变化 |

A07 不要求跨 GPU、驱动、系统或不同渲染器版本的逐字节像素相同。固定环境比较时间状态与关键帧；涉及抗锯齿等差异时采用明确容差，并用真实成片复核。

Three.js 的测试不能只有函数 mock；至少在实际目标环境中做一次混合场景的真实抓帧或短片渲染。若当前执行环境不能完成，报告具体未验证项，不把静态检查写成渲染通过。

## 12. 实施顺序与完成定义

### M1：先让效果看得见，并沿用同源实现

选择一个真实的 AI 科普或 Skill 介绍 Work。同步调整相关规则，接通可执行 Visual Plan、实际文字、完整 Scene 播放、确认关联及同源 Draft。使用现有 GSAP 能力先跑通，不等待组件库扩建。

完成定义：用户可以从可见效果确认方向；预演中的场景代码继续用于 Draft；完成一次指定 Scene 的局部修改；没有新加一次必经人工审批。

### M2：增加可复用的解释动作与 Three.js 样例

从本地真实案例选少量高价值 GSAP 动作和一到两个 Three.js 效果，按现有适配器接入。至少用不同内容绑定验证复用，同时检查信息密度、拖动和实际渲染。

完成定义：效果不是一次性复制代码；关键文字与效果同步；本地实际渲染通过；没有把所有 Scene 改成相同的粒子或镜头模板。无需以组件目录数量作为验收条件。

### M3：用真实交付检验返工是否下降

完成局部差异查看、配音重定时检查和少量结果记录。基于真实案例调整组件检索信息、可配置边界和需要沉淀的效果；用户继续主导完整组件库的内容选择。

完成定义：可以解释至少一个重复返工问题是否减少，或者为什么没有减少。没有证据时如实保留假设，不继续增加规则掩盖问题。

这三个阶段是实施拆分，不是新增三轮产品审批。Codex 按现有开发授权推进可完成部分；真正需要用户判断的是具体作品的设计选择与已定义的权限边界。

## 13. 成效度量与风险控制

### 13.1 最小观察指标

从少量可比的真实 Work 开始，建议覆盖不同文字密度及至少一种正式音频路径。先记录基线，不立即承诺固定改善百分比。

| 指标 | 定义与用途 |
|---|---|
| 总交付投入 | 从开始制作到最终接受的投入；包含预演迭代，防止只把返工前移 |
| Plan 后方向性返工 | 获批后因“实际效果与预期不同”而重做的 Scene / 已确认 Scene；新增需求单独记 |
| 修改影响范围 | 每条反馈实际改了哪些 Scene；观察是否仍因局部问题重做整片 |
| 有效复用 | 沿用公共组件或效果实现，通过绑定完成不同用途；完整组件与效果模块分开统计 |
| 信息保留与阅读问题 | 必须呈现的信息是否遗漏、过度简化或看不清；不能以高复用率掩盖退化 |

记录放入现有 Work 备注或运行元数据即可。不新增必填日报、复杂看板或 Agent 自评分体系。暂停等待用户录制/批准的时间与制作、返工时间区分。

### 13.2 主要风险

- **预演变成另一轮完整制作**：坚持同源实现，不做可丢弃的平行演示；先验证决定方向的内容，把非关键精修留后。
- **追求视觉奇观导致解释变少**：用必须上屏的信息和实际阅读检查约束结果，而不是靠“看起来不像 PPT”。
- **技术复用变成模板同质化**：复用动作机制，内容结构和叙事编排仍按具体主题设计。
- **Three.js 兼容或性能不稳定**：先小样实际抓帧、固定依赖、验证就绪和释放；有批准的降级才降级。
- **本地代码已超前于公开基线**：先识别已存在能力，仅补缺口，不重复造轮子或覆盖本地开发。
- **未来设计被误删**：未纳入本轮不等于取消；在原 PRD/索引中保留并标明后续范围。
